# Appliance client guide

This directory is one Expo application for web, iOS, and Android. Use
TypeScript and Bun for every app-side source file, build script, and test.
Expo Go is not supported because the app contains a custom native module.

## Boundaries

- Keep Expo Router files thin. Put screens, reusable components, controllers,
  and platform adapters in focused modules instead of growing a single route.
- Rust owns credentials, profiles, durable messages, device synchronization,
  retries, protocol validation, and shared API models through
  `appliance-store`, `appliance-sync`, `appliance-runtime`, and
  `appliance-service`.
- TypeScript owns UI state, presentation, navigation, permissions, and platform
  API orchestration. It must not reimplement Rust protocol or persistence
  semantics.
- Keep web, iOS, and Android behavior shared unless a platform adapter is
  required. Make platform-specific limitations explicit.
- Native application projects are generated by Expo Continuous Native
  Generation. Change authored modules, configuration, or scripts rather than
  patching generated application projects.

## Generated boundaries

Do not hand-edit `src/generated/api.ts` or generated files beneath
`modules/appliance-native`. Regenerate the owning boundary:

```sh
bun run api:generate
bun run native:bindings
bun run build:web
```

Use `api:generate` after Rust API model changes, `native:bindings` after native
Rust surface changes, and `build:web` after changing the embedded web client.

## Checks

```sh
bun install --frozen-lockfile
bun run verify
```

Use `bun run native:verify` when native bindings change and both mobile
toolchains are installed. Use `bun run ios`, `bun run android`,
`bun run release:ios`, or `bun run release:android` for actual native builds;
these wrappers own native preparation, installation, and launch.

Keep tests beside the TypeScript module they exercise. Prefer observable
behavior and lifecycle tests over snapshots of implementation text.
